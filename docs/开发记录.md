# 开发记录

本文件是恢复工程后续功能记录的唯一更新入口，也是所有开发者和 AI 接手本项目时必须遵守的开发记录规则。一个功能只保留一条记录；修复同一功能时更新原记录及验证结果，不重复追加状态描述。`README.md` 只写使用方法，其他原包文档保留为历史快照。

## 所有开发者和 AI 必须遵守的记录与交付规则

1. **先读后改**：开始任何开发前，先阅读本文件、`README.md`、`docs/开发进度.md`、`docs/开发交接与备份说明.md` 和 `docs/TEST_REPORT.md`，再检查当前 Git 分支、工作区和最近提交；不得仅凭聊天摘要或旧截图判断状态。
2. **只记录真实完成的功能**：功能必须已经在目标环境中可运行，并有对应的构建、测试或人工验收证据，才能标记为“已完成”。代码写完、构建通过或浏览器预览通过，不等于 Electron 原生窗口、托盘、跨平台或联网功能已经完成。
3. **一项功能一条记录**：新增功能时新增一条记录；修复已有功能时更新原记录的实现、验证、限制和错误原因，禁止重复追加同一功能的多条状态记录。多次记录后应合并重复内容，保留最新结论和必要的历史原因。
4. **必须填写错误原因**：每次验证失败、回滚或发现旧结论不准确，都要在对应功能记录的“错误及原因”中写清现象、原因（若尚未查明则明确写“原因未查明”）、修复或规避方式，以及当前剩余风险；不得把推测写成已修复。
5. **验证后再保留**：未通过真实验证的实验代码、截图和结论不得写成可用功能；应标记为“待验收”或移除误导性记录。历史资料可以保留，但必须注明“历史快照”，不能让它冒充当前版本。
6. **完成后同步 Git**：每项真实可用的重大功能完成并更新本文件后，运行相关测试，检查 `git diff` 和 `git status`，提交清晰的 commit，并推送到当前远端分支。推送失败时必须在记录中写明失败原因和未同步状态，不能声称已上传。
7. **交接必须可复现**：提交记录、文档、测试证据和当前限制要能让下一位开发者或 AI 在另一台电脑上复核。不要把未提交的本地文件、被 `.gitignore` 忽略的构建产物或聊天中的口头说明当作已交付内容。

执行顺序固定为：**阅读文档 → 检查 Git → 修改实现 → 真实验证 → 更新本文件（去重并填写错误原因）→ 提交并推送 → 再次核对远端提交**。

### 本轮错误及原因

- 当前 Windows 的 Vite 开发服务器在依赖预优化时出现目录访问拒绝和 React CJS 文件解析失败，而同一依赖下生产构建正常。原因与当前 pnpm 依赖目录/沙盒访问有关，尚未完全定位；网页验收改用生产构建和自带 `127.0.0.1` 静态服务器完成。
- 第一版网页 smoke 用 `file://` 加载生产文件，Document Picture-in-Picture 需要安全网页上下文，因此无法作为悬浮窗验证环境。测试已改为临时监听 `127.0.0.1`，并通过注入受控窗口验证 React portal 与失败回退。Electron 自动化仍不能代替真实 Chrome/Edge 的系统级置顶小窗验收。
