# 凡人流修仙桌宠游戏需求文档

- 文档版本：v1.0
- 文档性质：产品需求基线与开发交接文档
- 项目暂定名：尘途修仙（未定名，发布前需检索）
- 当前状态：需求与设计阶段；尚未创建客户端、服务器、角色素材或安装包
- 使用方式：后续开发者或 AI 应先阅读本文件，再检查实际项目环境；不得把设计目标描述为已实现功能

## 1. 文档约定

- **已确认**：用户明确提出或接受的要求。
- **设计基线**：为推进开发提出的默认方案，允许通过测试调整。
- **待验证**：需在技术验证、实际部署或用户测试中确定，不阻碍开始原型开发。
- **P0**：首个可交付版本必须实现。
- **P1**：首个内容完善版本优先实现，但不阻碍技术原型交付。
- **P2**：后续版本，不纳入首版承诺。

## 2. 产品目标与已确认需求

### 2.1 产品目标

制作一款适合桌面常驻、短时操作的联网修仙养成游戏。玩家从散修开始，通过潜修、经营洞府、炼丹炼器、探索秘境与同事合作，逐步提升境界。

核心体验：**各自在桌面潜修，偶尔结伴探索；角色成长能够通过桌宠外观与行为被看见。**

### 2.2 已确认需求

| 编号 | 要求 |
|---|---|
| C-01 | 采用类似《凡人修仙传》的凡人流修仙气质，不采用办公室恶搞主题 |
| C-02 | 常驻桌面角落的小窗口可以收起为桌宠 |
| C-03 | 必须具有服务器，同事可以联网一起玩 |
| C-04 | Windows 与 macOS 完全互通，共用角色与世界数据 |
| C-05 | 第一批玩家约 10 人 |
| C-06 | Windows 最低支持 Windows 10 |
| C-07 | macOS 面向 2024 年至今使用的近年版本，具体版本需映射确认 |
| C-08 | 支持 Intel Mac 和 Apple Silicon Mac |
| C-09 | 先制作原创 Q 版替代角色，不使用原作人物模型 |
| C-10 | 先形成设计与需求文档，再开始搭建 |
| C-11 | 当前为非盈利、同事之间游玩的项目 |

### 2.3 素材与原创要求

借鉴凡人流题材的成长、准备与机缘特点；人物、地名、功法、门派、剧情和美术原创。不得提取或分发原作、动画或其他游戏资产。第三方字体、图标、音效和素材应记录来源及许可。

非盈利不等于获得版权许可。本项目已决定使用原创角色，因此不以取得原作授权作为开发前提。

## 3. 用户与使用场景

- 玩家：约 10 位同事，设备包含 Windows PC、Intel Mac 与 Apple Silicon Mac。
- 场景：工作或日常使用电脑时低干扰常驻；用户主动短时打开查看与安排任务。
- 操作时长：查看与领取约十几秒，调整任务或组队约一至几分钟。
- 不要求固定时刻上线，不因队友关闭客户端而让探索失败。
- 不读取工作内容、不监听键盘、不申请录屏权限，不展示玩家的“工作/摸鱼时长”。
- 公司设备安装和联网须遵守单位规定，本软件不提供隐藏进程或绕过管理功能。

## 4. 首版范围

### 4.1 P0：首个可交付版本

1. 三种客户端构建目标：Windows x64、macOS Intel x64、macOS Apple Silicon arm64。
2. 原创 Q 版桌宠、洞府窗口、托盘或菜单栏入口、基本动画。
3. 邀请码注册、登录、服务器存档、跨设备角色同步。
4. 炼气一至十三层、筑基突破与筑基初期基本状态。
5. 潜修、离线结算、主任务切换、一门可用功法。
6. 静室、药园、丹房、基础法器与基础材料循环。
7. 单人历练、一种异步组队秘境。
8. 宗门创建/加入、公共贡献与至少一种设施升级。
9. 服务端权威、幂等领奖、断线恢复、备份与恢复。
10. 安装包及对应平台基础测试。

### 4.2 P1：首版内容完善

- 扩展至三门主修功法、约十二件法器、六种灵草与六张丹方。
- 三处单人历练地点、两种组队秘境、约二十条奇遇。
- 基础炼器台、三种宗门设施、洞府拜访、药园互助与预设传音符。
- 更多成长外观、探索报告表现与简短回放。

数量为范围控制目标，不是未经测试的硬性内容承诺。

### 4.3 P2：暂不实施

结丹及更高境界、完整灵兽养成、自由交易、拍卖行、自由聊天、公共匹配、实时操作战斗、强制 PvP、跨服排行、付费、广告、抽卡。

## 5. 游戏整体流程

### 5.1 初次进入

安装 → 邀请码注册/登录 → 创建角色 → 选择五行亲和 → 获得洞府和入门功法 → 完成潜修与药园引导 → 进入日常修行。

### 5.2 单人循环

潜修积累修为 → 药园产出 → 炼丹/制作法器 → 历练获取材料 → 升级洞府和搭配 → 准备突破 → 境界提升并解锁内容。

### 5.3 多人循环

加入宗门 → 贡献公共材料 → 发起探索 → 同事加入并确认准备 → 出发 → 服务器自动结算 → 个人领奖 → 提升角色或建设宗门。

### 5.4 桌面循环

展开窗口安排任务 → 收起为桌宠 → 桌宠展示任务动画 → 玩家主动查看通知 → 展开查看结果。

### 5.5 离线循环

关闭客户端 → 服务端按时间与规则记录进度 → 再次登录 → 同步任务状态 → 展示并领取离线收益。

## 6. 功能需求

### FR-01 桌宠与窗口（P0）

- 提供洞府窗口、桌宠、隐藏到托盘/菜单栏三种展示状态。
- 窗口收起为桌宠不得中断修行或退出账号。
- 桌宠可拖动、缩放，支持置顶开关、静音与隐藏。
- 单击桌宠展开洞府；右键或等效菜单提供快捷操作。
- 提供手动鼠标穿透模式，通过托盘/菜单栏可可靠恢复交互。
- 默认不抢焦点、不发声音、不强制置顶；提示气泡可关闭。
- 保存当前设备的窗口位置、缩放和偏好。
- 多屏变化后把窗口恢复到可见区域；休眠唤醒后重新同步。
- 全屏应用与 macOS 桌面空间的表现需验证并说明限制，不保证桌宠覆盖所有全屏场景。

**验收**：三种目标平台可以切换状态、拖动和恢复窗口；启用穿透后仍有明确的恢复入口；不影响其他应用正常输入。

### FR-02 原创角色与动画（P0）

- 制作一套原创 Q 版修士占位资源，优先采用 2D 精灵动画。
- 至少具有待机、打坐、行走、炼丹、御剑五类基础表现；可先用简化帧数。
- 动画反映当前任务，不承担修为或奖励计算。
- 动画资源与角色规则分离，便于替换。
- 收起到托盘后暂停不必要的渲染。

**验收**：任务变化后表现一致；替换资源不需修改服务端规则；素材来源明确。

### FR-03 账号与角色（P0）

- 使用邀请码注册；邀请码可限制次数、失效或由管理员停用。
- 初版采用用户名与密码，创建昵称和角色。
- 初版每个账号在一个世界内拥有一个角色，不开放多角色经济系统。
- 密码使用安全哈希保存，登录接口限流。
- 登录令牌使用系统安全存储机制，不写入普通明文配置或日志。
- 提供注销及管理员协助重置密码流程，管理员不得查看原密码。

**验收**：无有效邀请码不能注册；错误登录受到合理限流；重启客户端后可安全恢复会话或要求重新登录。

### FR-04 跨平台与多设备（P0）

- 所有客户端使用同一套服务端接口与数据规则。
- Windows 与 Mac 可以进入同一世界、同一宗门和同一队伍。
- 同一账号换设备后保持角色、物品、洞府、任务一致。
- 本地外观偏好按设备保存，不覆盖另一台设备的窗口位置。
- 多设备同时在线时，以服务端状态为准；冲突请求失败后刷新，不允许重复收益。
- 协议版本不兼容时明确提示更新，不能继续执行错误交易。

**验收**：Windows 发起队伍，Intel Mac 和 Apple Silicon Mac 均可参加；同账号在两台设备重复领奖只获得一次奖励。

### FR-05 修炼与任务（P0）

- 境界首版为炼气一至十三层与筑基初期。
- 角色同时执行一个主要任务：潜修、参悟、炼丹/炼器或历练；设施被动生产独立运行。
- 任务显示开始时间、预计完成时间、收益或效果以及中止后果。
- 切换潜修前结算截至切换时的进度，避免丢失或重复计算。
- 进入有耗材的制作或探索前明确确认；开始后中止规则必须可见。
- 初版关键任务不强制手动控火或实时点击。

**验收**：切换任务、重启客户端和更换设备不会重算同一段修为；已占用角色的任务不能重复开始。

### FR-06 离线收益（P0）

- 使用服务器时间，根据起点、任务与收益参数结算，不信任电脑时钟。
- 设计基线为潜修最多累积 24 小时待领取收益，后续可随洞府扩大。
- 药园成熟后停止生长但不枯萎；制作与探索到时正常完成。
- 长期离线不死亡、不损失已拥有的资源。
- 收益参数变化应分段结算或先结清旧参数，不追溯套用新加成。

**验收**：修改本地时间无额外收益；连续短时领取与等价时段一次领取在允许的取整误差内一致；超过上限不继续累积。

### FR-07 灵根与功法（P0/P1）

- 五行亲和影响专长，不随机产生永久劣等账号。
- P0 实现一门主修功法，P1 扩展稳健潜修、炼丹经营、隐匿探索三条路线。
- 允许后期调整路线，具体成本待平衡测试。
- 效果必须可理解且显示生效条件，不堆大量隐藏百分比。

### FR-08 突破（P0）

- 条件包含修为、功法进度与准备材料，玩家主动确认后执行。
- 提前显示成功率、消耗与失败后果，结果由服务器生成并持久化。
- 失败可损失部分材料并调息，但不永久毁号、不掉大境界。
- 失败产生感悟，关键进阶提供有限次数保障；具体概率与保障次数配置化。
- 寿元仅为剧情信息，初版不实行现实时间死亡。

**验收**：条件不足不能突破；重复提交不重复扣材料或重新随机；失败后角色仍可继续成长。

### FR-09 洞府与生产（P0/P1）

- P0：静室、药园、丹房；P1：炼器台。
- 设施升级展示成本、效果和前置条件。
- 配方展示材料来源、耗时与结果；服务器校验材料并原子扣除。
- 已完成产物不会因未及时领取而消失。
- 药园种植作为设施被动任务，不占用角色主任务。
- 初版炼丹/炼器由角色执行，不同时开启多个主任务。

**验收**：材料不足不能开始；任务完成后重复领取无重复物品；设施升级与生产规则一致。

### FR-10 行囊与法器（P0）

- 资源至少包含灵石、灵草、矿材、妖兽材料、宗门贡献。
- 支持物品数量、用途和来源说明。
- 法器提供攻伐、护身、辅助三个槽位，明确基础属性与特色效果。
- 探索出发后锁定该次装备快照，避免途中改装影响已开始的结果。
- 不做强化失败碎装备；贡献不可直接转让。
- 初版不设置付费扩容或容易导致奖励丢失的背包容量限制。

### FR-11 单人历练（P0）

- 展示推荐境界、耗时、危险程度、可能收益和损失。
- 提供稳妥采集、寻觅机缘、深入探索等策略，P0 可先实现一至两种。
- 结果包含材料、事件和可理解的成败原因。
- 失败主要损失时间、消耗品和部分本次收益，不掉已装备法器。
- 战斗自动结算，不要求在线实时操作。

### FR-12 异步组队秘境（P0）

- 设计基线为二至四人组队；允许单人参加对应低难度内容。
- 队长创建队伍，成员加入并确认职责、装备和消耗品。
- 队伍准备阶段成员可退出；出发前变更关键配置需重新确认。
- 队长只可在条件满足、成员确认后出发，出发后不可新增成员。
- 未出发时不提前永久扣除探索消耗品；出发时统一校验与扣除。
- 同一角色不得同时参加多个已出发探索。
- 已出发队伍不因客户端关闭或断线中断。
- 奖励以个人掉落为主，不要求抢夺或人工分配。
- 返回队伍有唯一结果与报告，不能重试随机。

**验收**：跨平台成员共同出发；全部客户端离线后仍可结算；服务重启后不会重复扣款、重复发奖或丢队伍。

### FR-13 宗门（P0/P1）

- P0 支持创建、邀请码/邀请加入、退出、成员列表、贡献与设施升级。
- 每个角色初版只能加入一个宗门。
- 定义宗主与成员权限；宗主退出前必须转让，或仅在无其他成员时解散。
- 贡献从个人资源扣除并进入公共建设账本，不允许重复捐献。
- P1 提供聚灵阵、藏经阁、公共药园三类设施。
- 小规模宗门可正常参与，不以大量人数作为强制前提。

### FR-14 社交互动（P1）

- 洞府拜访、药园照料、突破协助、预设传音符。
- 互动次数受规则限制，双方收益清晰，不可无限刷取。
- 可以关闭来访气泡与社交通知。
- 不展示在线时长排行，不据在线状态推断工作情况。

### FR-15 通知与网络状态（P0）

- 通知覆盖任务完成、探索结果、队伍邀请与重要系统消息。
- WebSocket 仅用于及时通知；断线后通过接口恢复完整状态。
- 显示离线/重连状态，不把离线预测显示为已领取资源。
- 网络不可用时允许查看缓存信息，不允许本地执行权威交易。
- 失败请求提供明确反馈；重试须幂等，禁止客户端盲目重复扣款请求。

### FR-16 管理与运维（P0）

- 管理员可管理邀请码、重置账号访问、查看错误与任务日志。
- 普通管理员操作不提供任意修改他人资源的游戏入口；维护修复需可审计。
- 定期数据库备份，至少完成一次实际恢复验证。
- 配置与密钥不提交到公开仓库；日志不记录密码、令牌等敏感信息。

## 7. 状态与数据基线

### 7.1 任务状态

任务使用明确状态：运行中 → 可领取/已结算 → 已领取；取消或失败有独立状态。不同任务可采用自动入账或领取入账，但一个任务必须只有一种规则。

建议：修炼按结算领取入账，探索结果先持久化再领取入账，生产完成后领取物品。所有状态变更在服务端完成。

### 7.2 队伍状态

准备中 → 已出发 → 已完成 → 全员已领取/归档；准备中可取消。已出发后不因队长离线而取消。

### 7.3 核心实体

账号、会话、角色、世界、亲和与功法、洞府设施、库存、法器、任务、配方、队伍与成员快照、探索结果、奖励领取记录、宗门与成员、贡献账本、幂等请求记录、审计事件。

### 7.4 一致性规则

- 资源不能为负，扣除与产出采用事务。
- 每份奖励具有唯一标识，每个玩家最多领取一次。
- 重复请求返回原有结果，不重新随机。
- 开始任务使用必要的角色状态锁或版本校验。
- 定时任务漏跑可通过启动恢复扫描或请求时惰性结算补齐。
- 时间统一使用服务端 UTC，客户端按本地时区展示。
- 数值精度、取整与上限统一定义，前后端不各自解释。

## 8. 界面信息结构

洞府窗口建议初始约 420 × 600，允许调整。主导航：修行、洞府、历练、宗门、行囊。

首页显示：角色与境界、当前任务、修为进度、突破条件、重要事件、产物汇总入口。

重要交易使用确认信息，尤其是突破、探索出发、资源贡献与任务中止。所有确认应展示实际成本及后果，而非泛化“确定吗”。

## 9. 技术建议与兼容要求

### 9.1 推荐架构（非已实现）

| 部分 | 建议 |
|---|---|
| 客户端 | Electron + React + TypeScript |
| 动画 | 透明窗口 + 2D 精灵动画，必要时引入 PixiJS |
| 服务端 | Node.js + TypeScript + Fastify |
| 数据库 | PostgreSQL |
| 通信 | HTTP API + WebSocket |
| 部署 | 单台服务器、Docker Compose、HTTPS 反向代理 |

初期不采用分服、微服务或复杂消息队列。安装包采用哪个 Electron 版本，需要同时核对 Windows 10 与 macOS 支持范围。

### 9.2 平台要求

- Windows 10 x64 及更新兼容系统，具体测试版本需记录。
- macOS 暂按 14 Sonoma 及更新版本规划；这属于年份描述的设计解释，需根据同事实际设备核对。
- Intel 和 Apple Silicon 分别构建或使用经验证的通用安装包。
- Mac 构建、签名、公证需要相应环境；在 Windows 上运行不代表 Mac 已通过验收。
- 不保证透明区域自动穿透在所有平台一致；P0 先保证手动穿透可用。
- 客户端升级与数据迁移保持兼容；自动更新可后置，首版可人工安装新版。
- 正式交付记录签名、公证情况及可能出现的系统安装提示，不能隐瞒未签名状态。

## 10. 非功能需求与验收目标

### 10.1 性能

- 服务端先按至少 10 个同时在线账号验收，不据此承诺大规模容量。
- 普通读取接口在测试环境下目标 p95 小于 1 秒；需记录服务器配置与网络条件。
- 桌宠建议 15–30 FPS，隐藏后停止不必要渲染。
- 暂定客户端常驻目标：参考设备上平均 CPU 不超过约 3%、内存不超过约 250 MB；这些是待测优化目标，不能作为现有能力宣传。
- 必须测试笔记本电量影响、休眠恢复和长时间常驻，不只测试短时动画。

### 10.2 安全与隐私

HTTPS；密码安全哈希；请求参数校验；登录与交易接口限流；账号权限校验；敏感数据不入日志；服务端验证所有交易。

只收集账号、角色和必要运维数据，不收集工作内容。若以后扩大分发范围，应重新评估隐私政策与合规要求。

### 10.3 可靠性

- 客户端与服务端重启后可恢复状态。
- 备份建议每日执行，初期恢复点目标 24 小时内；保留周期与存储位置部署时确定。
- 恢复演练必须验证角色、库存、运行任务和奖励记录，不仅验证数据库文件可打开。
- 执行数据库迁移前备份，失败有回滚或前向修复方案。

## 11. 初始数值与内容原则

- 首次筑基目标约一至两周轻度游玩，待测试调整。
- 关键概率、耗时、成本、上限与奖励配置化，不散落在界面代码。
- 不做无限吃丹造成巨大差距；不让晚加入玩家无法参加同事玩法。
- 功法与宗门收益需要有来源和消耗闭环。
- 风险提前可知，失败有解释，不以恶意损失制造留存。
- 不使用要求固定时刻上线的奖励或连续签到断签惩罚。

## 12. 开发阶段与退出标准

### 阶段 A：环境检查与桌宠技术原型

检查现有目录、运行环境、构建条件；建立客户端骨架；制作原创占位动画；完成窗口切换、托盘/菜单栏、拖动、穿透、多屏和休眠验证。

退出标准：至少完成 Windows 实测；Mac 两架构完成实测或明确记录尚缺环境。未实测不能标记跨平台完成。

### 阶段 B：服务端与单人闭环

完成数据库、登录、权威存档、潜修与离线结算、药园、炼丹、法器、历练和筑基突破。

退出标准：从创建角色到突破可走通；改本地时间、重试与重启不导致资源异常。

### 阶段 C：多人闭环

完成邀请码、宗门、跨平台组队、异步结算与个人奖励。

退出标准：两人以上共同出发并领奖；离线和服务重启可恢复；10 人基础联调通过。

### 阶段 D：内容与发布

补充 P1 内容、优化美术与性能、构建安装包、验证备份恢复、完善使用说明。

退出标准：兼容矩阵、安装测试与关键验收用例有记录；素材许可清单完整。
